# PocketBase Toolkit - 기획 평가

---

## 좋은 점

### 1. 진입 장벽이 낮다
Cloudflare Tunnel 덕분에 서버 포트 개방, 공인 IP, DNS 설정 없이도 배포가 가능하다.
VPS 경험이 없는 사람도 `make deploy` 한 번으로 서비스를 올릴 수 있다는 점은 큰 강점이다.

### 2. PocketBase와 Docker의 궁합이 좋다
PocketBase는 단일 바이너리 + SQLite 파일 하나로 동작하므로 컨테이너화가 자연스럽다.
볼륨 마운트 하나로 데이터 영속성이 해결되고, 이미지 크기도 10MB 수준으로 가볍다.

### 3. 범위가 적절하다
백업, 복원, 업그레이드, 배포 자동화까지 실제 운영에 필요한 것들을 커버하면서도
과도한 추상화나 불필요한 의존성 없이 shell script + Makefile 수준으로 유지한다.

### 4. 대안 경로가 있다
Cloudflare Tunnel을 기본으로 하되 Caddy 옵션을 남겨둬서,
Cloudflare에 묶이고 싶지 않은 사용자도 수용할 수 있다.

---

## 한계점

### 1. SQLite의 구조적 한계
PocketBase는 SQLite를 사용하므로 **쓰기 동시성이 낮다.**
트래픽이 몰리는 서비스에는 적합하지 않고, 수평 확장(여러 인스턴스)이 불가능하다.
이 툴킷은 1서버 1인스턴스 구성만 지원하며, 그 이상을 원한다면 PocketBase 자체가 한계다.

### 2. Cloudflare 의존성
기본 구성이 Cloudflare Tunnel에 의존하므로, Cloudflare 장애 시 서비스 접근이 불가능하다.
또한 모든 트래픽이 Cloudflare를 경유하므로 데이터 프라이버시에 민감한 서비스에는 부적합하다.

### 3. 운영 가시성 부재
로그 수집, 메트릭, 알림 구성이 없다.
장애가 발생해도 능동적으로 감지할 수단이 없고, 사후에 Docker 로그를 직접 뒤져야 한다.
소규모 프로젝트라면 감수할 수 있지만, 한계임은 분명하다.

### 4. 백업의 신뢰성
`scripts/backup.sh`가 실행 중인 SQLite 파일을 단순 복사하는 방식이라면
쓰기 중간에 복사될 경우 파일이 손상될 수 있다.
PocketBase API의 백업 엔드포인트(`/api/backups`)를 활용하거나
SQLite의 `.backup` 명령을 써야 안전하다. 구현 시 주의가 필요한 부분이다.

### 5. 보안 설정이 명시적이지 않다
Admin UI(`/_/`)가 기본적으로 외부에 노출된다.
Cloudflare Access로 Admin UI 접근을 제한하는 방법이나,
`PB_ADMIN_EMAIL` / `PB_ADMIN_PASSWORD` 이후 계정 보안 설정에 대한 안내가 없다.

---

## 적합한 사용 사례

- 사이드 프로젝트 / 개인 서비스
- 프로토타입 또는 MVP 단계 서비스
- 소규모 팀 내부 도구
- Supabase, Firebase 대신 셀프호스팅을 원하는 경우

## 적합하지 않은 사용 사례

- 동시 쓰기가 많은 고트래픽 서비스
- 데이터가 Cloudflare를 경유하면 안 되는 서비스
- 99.9% 이상의 SLA가 필요한 서비스
- 팀 규모가 커서 권한 관리가 복잡한 경우

---

## 총평

PocketBase 자체가 "빠르게 올려서 쓰는" 도구이고, 이 툴킷은 그 철학을 잘 따른다.
과도하게 엔터프라이즈화하지 않고 실용적인 범위 안에서 반복 사용 가능한 템플릿을 만드는 것이 목표인데, 그 목표에는 잘 맞는 기획이다.

단, 백업 신뢰성과 Admin UI 보안은 구현 단계에서 반드시 챙겨야 할 부분이다.
